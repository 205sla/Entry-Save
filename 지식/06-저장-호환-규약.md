# Entry Save 저장 호환 규약 — 확장프로그램 개발자용

다른 엔트리 확장프로그램에서 저장 기능을 만들 때 **Entry Save Manager와 같은 저장본을 읽고 쓰기 위한 규약**입니다. 기존 저장 방식을 그대로 사용하므로, 사용자가 확장프로그램을 바꾸어도 같은 브라우저 저장 공간에서 진행도를 이어갈 수 있습니다. 엔트리 공식 표준이 아닌 이 프로젝트의 호환 규약입니다.

확인일은 **2026-09-29**입니다. **저장 키와 JSON 형식은 공개 v1.3.9와 같고, 복원·실행 제어 규칙과 예제는 v1.3.10 개발안을 기준으로 합니다.** 확인 당시 공개 코드는 [v1.3.9 커밋](https://github.com/205sla/Entry-Save/tree/91c248e7536bbd156679577a44e99021d49f01b7)이며, v1.3.10 런타임 수정은 이 문서 공개에 포함되지 않습니다. 문서의 예제 함수는 직접 구현할 때 사용할 보조 코드이며, 설치된 Entry Save Manager가 공개하는 API가 아닙니다.

| 항목 | 공개 v1.3.9 | 이 문서의 호환 기준 / v1.3.10 개발안 |
| --- | --- | --- |
| 저장 키·JSON·값 타입 | 이 문서와 같음 | 기존 저장본 형식 유지 |
| 다른 작품의 복원 대상 | ID 또는 이름으로 첫 일치 대상을 선택 | 이름만 비교하여 작품 간 ID 충돌 방지 |
| 현재 대상의 저장 자격 | 저장된 이름은 검증하지만 현재 대상의 이름은 재검증하지 않음 | 현재 대상도 `@` 이름인지와 예약 변수 여부 검증 |
| 자동 복원·재개 | 감지 경로가 겹치거나 일시정지에서 재개할 때 복원이 반복될 수 있음 | 실행당 한 번, 일시정지 재개 시 반복 안 함 |
| 함수 이름·재연결 | 문자열 포함 검색 폴백과 초기 연결 재시도 횟수 제한이 있음 | 정확한 제목 비교와 지속 재연결 |

새 구현은 오른쪽 기준을 따르세요. 공개 v1.3.9와 함께 검증할 때는 위 차이를 고려해야 하며, 데이터 형식 호환이 모든 실행 동작의 일치를 뜻하지는 않습니다. [shared.js](../ES/shared.js)와 [inject.js](../ES/inject.js)는 체크아웃한 버전의 실제 구현입니다.

## 1. 무엇을 맞추면 호환되나요?

| 구현 범위 | 맞춰야 하는 내용 |
| --- | --- |
| 저장본 읽기·쓰기 | 같은 페이지 저장 공간, 저장 키, JSON 필드, 값 타입, 복원 대상 선택 규칙 |
| 기존 작품의 저장 기능 지원 | 위 항목 + `@저장`, `@가져오기`, 실행 시 자동 복원, `@확장프로그램` 변수 |

저장본 관리 도구는 첫 번째 범위만 구현할 수 있습니다. Entry Save Manager용으로 만들어진 작품까지 실행하려면 두 번째 범위도 구현해야 합니다. Entry Save Manager가 함께 설치되어 있어야 하는 구조는 아닙니다.

작품 제작자는 저장할 변수·리스트 이름 앞에 `@`를 붙이고, 매개변수 없는 `@저장` 함수를 호출합니다. 선택적으로 문자/숫자값 입력 하나를 받는 `@가져오기` 함수와 `@확장프로그램` 변수를 만듭니다. 자세한 제작법은 [README의 작품 제작 가이드](../README.md#-작품-제작-가이드)를 참고하세요.

## 2. 저장 공간과 키

**`window.Entry`가 실행되는 엔트리 페이지 프레임의 `window.localStorage`**에 JSON 문자열을 저장합니다. `chrome.storage.local`, 확장 팝업의 `localStorage`, 서버 DB에만 기록하면 이 저장본과 연결되지 않습니다. Content script의 Web Storage는 호스트 페이지와 공유됩니다. [Chrome 저장소 문서](https://developer.chrome.com/docs/extensions/reference/api/storage#can-extensions-use-web-storage-apis)

호환은 같은 브라우저 프로필과 같은 origin·저장 파티션 안에서 성립합니다. Origin은 프로토콜·호스트·포트의 조합이므로, `https://playentry.org`와 다른 서브도메인·로컬 개발 서버의 저장본은 자동 공유되지 않습니다. 브라우저/프로필 변경이나 사이트 데이터 삭제 후 복구·기기 간 동기화는 이 규약의 기능이 아닙니다. [MDN localStorage 문서](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

| 동작/페이지 | 사용할 키 |
| --- | --- |
| `/project/<id>` 저장·자동 복원 | `entry_save_<id>` |
| `/noframe/<id>` 저장·자동 복원 | `entry_save_<id>` |
| `/ws/<id>` 저장·자동 복원 | `entry_save_ws_<id>` |
| `/iframe/<id>` | 부모 페이지가 `/ws/`이면 `entry_save_ws_<id>`, 작품보기이면 `entry_save_<id>` |
| `@가져오기(<다른 작품 ID>)` | 호출 페이지와 무관하게 `entry_save_<다른 작품 ID>` |
| `@가져오기(<현재 작품 ID>)` | 현재 페이지의 키. `/ws/`라면 `entry_save_ws_<현재 작품 ID>` |

현재 작품 ID는 `Entry.projectId`를 우선하고, 없으면 `/ws/`, `/project/`, `/iframe/`, `/noframe/` URL에서 추출합니다. `/ws/new`처럼 ID가 아직 없는 작품에는 임의의 공용 키를 만들지 말고 작품 저장 후 ID가 생길 때까지 기다립니다.

`@가져오기` 인자는 실행 시 평가된 값을 문자열로 바꾸고 양끝 공백을 제거합니다. 현재 검증식은 `/^[a-f0-9]{8,}$/i`입니다. 24자리로만 제한하지 않으며, 전체 URL은 인자로 받지 않습니다. 대소문자는 변환하지 않으므로 실제 작품 ID 문자열을 그대로 사용하세요. 현재 ID와 같은지 비교할 때도 문자열이 정확히 같아야 합니다.

`/iframe/` 경로만으로는 만들기/작품보기를 구별할 수 없습니다. 부모 페이지 정보를 받아야 합니다. 현재 구현은 pageType이 미해결이면 `project` 키로 임시 접근합니다. 이 폴백으로 만들기 데이터가 섞이지 않도록 호환 확장에서는 부모의 타입을 확인한 뒤 저장 기능을 활성화하는 편이 좋습니다. 과거 키 `entry_save_project_<id>`는 현재 읽기 대상이 아니며 자동 마이그레이션도 하지 않습니다. [키 변천사](04-스토리지-키-규칙.md)

## 3. JSON 저장 형식

키 하나에 다음 객체를 `JSON.stringify()`한 **문자열 하나**를 저장합니다. 별도의 래퍼 객체, 압축, Base64 인코딩은 사용하지 않습니다.

```json
{
  "variables": [
    { "id": "level01", "name": "@레벨", "value": 7 },
    { "id": "name001", "name": "@이름", "value": "엔트리봇" },
    { "id": "clear01", "name": "@클리어", "value": true },
    { "id": "quest01", "name": "@진행퀘스트", "value": null }
  ],
  "lists": [
    { "id": "bag0001", "name": "@인벤토리", "array": ["열쇠", 3, false, null] },
    { "id": "log0001", "name": "@기록", "array": [] }
  ],
  "savedAt": "2026-09-29T00:00:00.000Z"
}
```

| 필드 | 작성 규칙 |
| --- | --- |
| `variables` | 변수 레코드 배열. 대상이 없으면 `[]` |
| `variables[].id` | 엔트리 변수의 `id_` 문자열을 그대로 사용 |
| `variables[].name` | `name_` 그대로. `@`로 시작하고 `@확장프로그램`이 아닌 이름 |
| `variables[].value` | `number`, `string`, `boolean`, `null` 중 하나 |
| `lists` | 리스트 레코드 배열. 대상이 없으면 `[]` |
| `lists[].id`, `lists[].name` | 리스트의 `id_`, `name_` 그대로. 이름은 `@`로 시작 |
| `lists[].array` | 위 값 타입만 담는 배열. 순서와 빈 배열을 보존 |
| `savedAt` | `new Date().toISOString()` 형식의 저장 시각 |

변수는 `Entry.variableContainer.variables_`에서, 리스트는 `lists_`에서 수집합니다. 리스트의 런타임 항목은 `{ data: 값 }` 형태이므로 저장할 때 `array_.map(item => item.data)`로 펼칩니다. 저장 JSON에 `{ "data": ... }`를 그대로 넣으면 해당 항목이 복원되지 않습니다.

숫자는 유한한 JSON 숫자로 작성하세요. `NaN`, `Infinity`, `undefined`, `BigInt`, 함수, 객체, 중첩 배열은 호환 값이 아닙니다. 현재 저장기는 타입을 미리 걸러내지 않고 `JSON.stringify()`하지만, 복원기는 아래 검증을 적용합니다. 직렬화 과정의 값 변환이나 실패에 의존하지 마세요.

**현재 예약 대상은 `@확장프로그램`이라는 변수입니다.** 이 변수는 저장·복원에서 모두 제외합니다. 같은 이름의 *리스트*에는 이 제외 처리가 없으므로, 기존 데이터의 해당 리스트는 일반 `@` 리스트로 처리해야 합니다. 새 작품에서는 혼동을 피하도록 이 이름을 변수에만 사용하세요.

`savedAt`은 복원 여부나 충돌 해결에 쓰이지 않습니다. 기존 리더는 이 필드가 없는 저장본도 읽습니다. 현재 저장본에는 `version`, `projectId`, 확장 ID 필드가 없고, 작품 구분은 저장 키로 합니다. 추가 필드는 현재 리더가 무시하지만 다음 저장 때 사라질 수 있으므로 필수 데이터나 확장 설정을 추가 필드에 의존시키지 마세요.

저장은 현재 대상 전체를 담은 스냅샷으로 키의 값을 교체합니다. 예전 레코드와 병합하지 않으며, 대상이 없으면 빈 배열 두 개를 기록합니다. 같은 키에 여러 탭이나 확장이 저장하면 마지막 쓰기가 남습니다.

## 4. 불러오기 규칙

1. 저장 키가 없으면 현재 값을 유지합니다. JSON 파싱 실패 또는 최상위 값이 객체가 아닌 경우(`null`, 배열 포함)도 복원을 중단하고 원본 저장 문자열은 남깁니다.
2. `variables`와 `lists`는 각각 배열일 때만 처리합니다. 한쪽이 없거나 잘못되어도 다른 쪽은 읽습니다. 유효하지 않은 레코드는 개별적으로 건너뜁니다.
3. 저장된 이름과 **현재 대상의 이름 모두** `@`로 시작해야 합니다. 변수의 경우 양쪽 모두 `@확장프로그램`이 아니어야 합니다. ID가 같아도 현재 이름에서 `@`를 제거했다면 복원하지 않습니다.
4. 아래 조건으로 현재 컨테이너 배열에서 **처음 일치하는 대상 하나**를 찾습니다. 없으면 건너뛰며, 변수·리스트를 새로 만들지 않습니다.
5. 변수는 값이 `null`이거나 `typeof`가 `number`/`string`/`boolean`일 때 `target.setValue(value)`로 복원합니다. 리스트는 `array`가 배열이어야 하며, 허용되지 않는 타입의 항목만 제거한 뒤 `target.array_ = values.map(value => ({ data: value }))`로 전체 교체합니다. 빈 배열도 정상 복원합니다.

| 불러오기 종류 | 대상 선택 조건 |
| --- | --- |
| 자동 복원 / `@가져오기(현재 ID)` | `현재.id_ === 저장.id` **또는** `현재.name_ === 저장.name` |
| `@가져오기(다른 ID)` | `현재.name_ === 저장.name`만 사용. ID는 비교하지 않음 |

자기 작품 복원은 “ID부터 찾고 없으면 이름 찾기”라는 두 단계 검색이 아닙니다. 위 OR 조건을 만족하는 첫 항목을 선택합니다. 이름은 공백·대소문자까지 정확히 비교하며, 여러 오브젝트의 같은 이름을 구분하는 별도 필드는 없습니다. 작품 안에서 저장 대상 이름을 고유하게 정하면 모호함을 피할 수 있습니다.

가져오기는 현재 실행 중인 값만 바꿉니다. 원본 작품의 저장본이나 현재 작품의 저장 키에 다시 쓰지 않습니다. 가져온 값을 현재 작품의 진행도로 남기려면 이후에 `@저장`을 호출해야 합니다.

## 5. 작품과 연결하는 런타임 동작

| 신호 | 호환 동작 |
| --- | --- |
| `@저장` 함수 호출 | 현재 namespace로 저장한 뒤 기존 함수 구현을 원래 `this`·인자로 호출하고 반환값을 유지 |
| `@가져오기` 함수 호출 | 평가된 작품 ID로 복원한 뒤 기존 함수 구현을 원래 `this`·인자로 호출하고 반환값을 유지 |
| 작품 실행 시작 | 현재 namespace에서 자동 복원한 뒤, 존재하는 `@확장프로그램` 변수를 숫자 `1`로 설정 |
| 정지 후 재실행 | 다시 자동 복원 |
| 일시정지 후 재개 | 같은 실행으로 취급하여 자동 복원 반복 안 함 |

`@저장` 호출을 가로챈 시점에 저장하므로 함수 본문 안에서 바꿀 값까지 미리 저장되지는 않습니다. 저장할 값의 변경을 끝낸 다음 이 함수를 호출하도록 안내하세요. 일반 변수 변경, 작품 정지, 탭 닫기는 저장 트리거가 아닙니다. `@확장프로그램`은 사용자가 만든 변수에만 설정하며 자동 생성하지 않습니다. 수동 `@가져오기` 자체는 이 플래그를 설정하는 동작이 아닙니다.

v1.3.10 개발안은 실행 상태 감지 후 300ms 뒤 복원하고, 500ms 간격으로 엔진·함수 연결을 확인합니다. 처음 연결했을 때 이미 실행 중이어도 복원하며, 전체화면 전환 등으로 `Entry.engine`이 바뀌면 새 엔진에 다시 연결합니다. 이 시간은 구현값이며, 모든 시작 블록보다 먼저 복원이 끝난다는 보장은 없습니다. 저장 데이터를 사용하는 작품은 초기 실행과 복원 시점이 겹치는 경우를 확인해야 합니다.

함수 연결을 구현할 때는 [inject.js](../ES/inject.js)의 다음 부분을 참고하세요. 공개 v1.3.9의 코드명으로 표시했으며, 개발안에서 보강한 동작은 구분했습니다.

| 코드 | 구현 시 확인할 점 |
| --- | --- |
| `extractFunctionName`, `findFunctionIdByName` | 함수 제목 추출. 새 구현에서는 제목 전체만 비교하고 부분 이름·본문 문자열 검색 폴백을 제거해야 함 |
| `getFuncParamKey`, `readCallBlockArg` | `paramMap`과 호출 인스턴스 `this.values`에서 평가된 인자 추출. 개발안은 편집을 반영하도록 호출 시점에 `paramMap`을 읽음 |
| `tryHookLoad` (개발안: `invokeLoad`) | 인자 검증과 현재 ID 예외 처리. 평가값이 없을 때만 정적 리터럴 탐색을 폴백으로 사용 |
| `tryHookSave`, `tryHookLoad`, `hookFunctionCalls` | `Entry.block['func_' + 함수ID].func` 연결. 개발안은 함수 생성·편집·스키마 교체를 계속 감시하여 재연결 |
| `watchEngineState`, `hookEngineToggleRun` | 엔진 상태 감지. 개발안의 `observeEngineState`가 실행당 한 번 복원과 일시정지 처리를 통합 |
| `URL_CHANGED` 메시지 리스너 | 이전 작품 정리. 개발안은 예약된 복원 취소와 자기 래퍼의 비활성화까지 처리 |

MAIN world에 접근해야 페이지의 `window.Entry`를 사용할 수 있습니다. 기본 Isolated world의 JavaScript 전역은 페이지와 분리되어 있습니다. 프레임 안에 런타임이 있는 경우까지 대응하려면 `all_frames: true`로 주입하고, 실제 `Entry`가 준비된 프레임에서만 동작하게 하세요. [Chrome content script 문서](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

부모의 pageType 전달은 [content.js](../ES/content.js)와 [프레임 핸드셰이크 설명](공통/entry-page-type-handshake.md)을 참고할 수 있습니다. `ENTRY_SAVE_MANAGER` 메시지의 `REQUEST_PAGE_TYPE`/`PAGE_TYPE`은 페이지 종류를 전달하는 내부 통신이며 저장 요청 API가 아닙니다. `PAGE_TYPE`은 부모 프레임에서 온 메시지인지와 값이 `ws`/`project`인지 검증합니다.

현재 공개된 `save()`/`load()` 전역 API, 확장 간 `sendMessage` API, 저장 완료 이벤트 계약은 없습니다. `content.js`에 있는 `SAVE_COMPLETE`/`LOAD_COMPLETE` 수신 분기는 현재 저장 코드가 보내는 완료 통지가 아닙니다. 다른 확장에서 그 이벤트를 기다리거나 임의의 `SAVE` 메시지를 보내 저장을 요청하지 마세요.

## 6. 저장·복원 보조 코드 예제

아래 코드는 **데이터 읽기·쓰기 부분만** 구현합니다. MAIN world에서 준비된 `Entry`, 실제 페이지의 `localStorage`, 확정된 작품 ID와 pageType을 넘기세요. 자동 실행 감지, 함수 후킹, 설치 플래그 설정, iframe 핸드셰이크는 앞 절의 규칙대로 별도로 연결해야 합니다. SPA 이동 또는 `Entry` 자체 교체 시에는 새 컨텍스트로 다시 생성하세요.

저장 시 허용되지 않는 값은 예외로 알리고 기존 저장본을 유지합니다. 읽기는 현재 리더와 같은 항목별 검증을 사용합니다. 저장소 접근/쓰기 오류는 호출자가 처리하고, 손상된 JSON은 `load()`가 `false`를 반환합니다. 이 반환값은 예제 보조 함수의 규칙입니다.

```js
function createEntrySaveAdapter({ entry, storage, projectId, pageType }) {
  const validId = (id) => typeof id === 'string' && /^[a-f0-9]{8,}$/i.test(id);
  if (!validId(projectId) || !['ws', 'project'].includes(pageType)) {
    throw new Error('확정된 작품 ID와 pageType이 필요합니다.');
  }
  const keyFor = (id, type) => 'entry_save_' + (type === 'ws' ? 'ws_' : '') + id;
  const isTargetName = (name) => typeof name === 'string' && name.startsWith('@');
  const isVariableName = (name) => isTargetName(name) && name !== '@확장프로그램';
  const isValue = (value) => value === null
    || ['number', 'string', 'boolean'].includes(typeof value);
  const canWrite = (value) => isValue(value)
    && (typeof value !== 'number' || Number.isFinite(value));

  function save() {
    const vc = entry.variableContainer;
    const variables = (vc.variables_ || [])
      .filter((v) => isVariableName(v.name_))
      .map((v) => ({ id: v.id_, name: v.name_, value: v.value_ }));
    const lists = (vc.lists_ || [])
      .filter((l) => isTargetName(l.name_))
      .map((l) => ({
        id: l.id_, name: l.name_, array: (l.array_ || []).map((item) => item.data),
      }));
    if (variables.some((v) => !canWrite(v.value))
        || lists.some((l) => l.array.some((item) => !canWrite(item)))) {
      throw new TypeError('저장 값은 유한한 숫자, 문자열, 불리언, null만 허용합니다.');
    }
    const data = { variables, lists, savedAt: new Date().toISOString() };
    storage.setItem(keyFor(projectId, pageType), JSON.stringify(data));
    return data;
  }

  function load(sourceProjectId = projectId) {
    const sourceId = String(sourceProjectId).trim();
    if (!validId(sourceId)) return false;
    const crossProject = sourceId !== projectId;
    const raw = storage.getItem(keyFor(sourceId, crossProject ? 'project' : pageType));
    if (!raw) return false;
    let data;
    try { data = JSON.parse(raw); } catch { return false; }
    if (!data || typeof data !== 'object' || Array.isArray(data)) return false;

    const vc = entry.variableContainer;
    const matches = (target, saved) => crossProject
      ? target.name_ === saved.name
      : target.id_ === saved.id || target.name_ === saved.name;

    for (const saved of Array.isArray(data.variables) ? data.variables : []) {
      try {
        if (!saved || !isVariableName(saved.name) || !isValue(saved.value)) continue;
        const target = (vc.variables_ || []).find((v) => (
          isVariableName(v.name_) && matches(v, saved)
        ));
        if (target && typeof target.setValue === 'function') target.setValue(saved.value);
      } catch (error) {
        console.warn('변수 한 항목을 복원하지 못했습니다.', error);
      }
    }
    for (const saved of Array.isArray(data.lists) ? data.lists : []) {
      try {
        if (!saved || !isTargetName(saved.name) || !Array.isArray(saved.array)) continue;
        const target = (vc.lists_ || []).find((l) => (
          isTargetName(l.name_) && matches(l, saved)
        ));
        if (target) target.array_ = saved.array.filter(isValue).map((value) => ({ data: value }));
      } catch (error) {
        console.warn('리스트 한 항목을 복원하지 못했습니다.', error);
      }
    }
    return true; // JSON 구조를 읽음. 모든 항목의 복원 성공을 뜻하지는 않습니다.
  }

  return { save, load };
}
```

자신의 확장에 연결할 호출 형태는 다음과 같습니다. 페이지 종류 판별을 생략하지 않도록 생성 함수를 사용했습니다.

```js
function connectSaveAdapter(resolvedProjectId, resolvedPageType) {
  return createEntrySaveAdapter({
    entry: window.Entry,
    storage: window.localStorage,
    projectId: resolvedProjectId,
    pageType: resolvedPageType, // 부모 정보를 포함해 판별한 'ws' 또는 'project'
  });
}

// 준비된 컨텍스트에서 생성한 adapter를 자신의 실행 감지/함수 후킹에 연결합니다.
```

## 7. 여러 확장과 함께 사용할 때

**여러 확장을 설치할 수 있지만, 같은 작품 런타임에서 저장·불러오기를 처리하는 확장은 하나만 활성화합니다.** 같은 JSON 형식을 사용하는 것만으로 실행 중복까지 해결되지는 않습니다. 공개 v1.3.9와 v1.3.10 개발안 모두 다른 확장과 담당자를 자동으로 정하거나 사용자 선택을 공유하는 기능이 없습니다.

### 7.1. 둘 다 동작하면 생기는 일

| 중복 동작 | 영향 |
| --- | --- |
| `@저장`을 각각 처리 | 같은 키에 두 번 쓰며 마지막 쓰기가 남음. 읽은 시점이나 수집한 값이 다르면 앞선 저장본을 덮어씀 |
| 실행 시작 시 각각 자동 복원 | 먼저 복원한 뒤 게임이 바꾼 값을 뒤늦은 복원이 다시 덮어쓸 수 있음 |
| `@가져오기`를 각각 처리 | 같은 호출에 복원이 반복되고, 함수 실행 순서에 따라 값이 달라질 수 있음 |
| 같은 함수를 계속 재후킹 | 각 확장이 상대의 래퍼를 다시 감싸 호출 경로가 길어지거나, 서로의 연결을 해제할 수 있음 |

`savedAt`이 더 최근인 저장본을 골라 병합하거나 중복 호출을 제거하는 기능은 없습니다. 같은 값을 두 번 저장했을 때 당장 문제가 없어 보이더라도, 자동 복원과 재후킹까지 안전하다는 뜻은 아닙니다.

현재의 `window.__entrySaveManagerLoaded`는 같은 프레임에 저장매니저 코드가 재주입되는 것을 막는 내부 플래그입니다. 초기화가 끝나기 전에도 설정되므로 정상 동작이나 담당자 선정을 증명하지 않습니다. `_isSaveMgrHook` 역시 래퍼 식별용이며 확장 간 잠금이 아닙니다. 작품의 `@확장프로그램 = 1`도 어떤 확장이 담당하는지, 몇 개가 실행 중인지 알려주지 않습니다.

### 7.2. 지금 사용자에게 안내할 처리 방법

1. 사용할 저장 확장을 하나 정합니다. 다른 확장에 별도 저장 기능 설정이 있으면 **저장·자동 불러오기 기능을 함께 끕니다.** 다른 도구 기능은 계속 사용할 수 있습니다.
2. 저장 기능만 끄는 설정이 없다면 브라우저 확장 관리 화면에서 그 확장 전체를 비활성화합니다. **Entry Save Manager 팝업에는 저장 기능 ON/OFF 설정이 없으므로**(공개 v1.3.9 및 v1.3.10 개발안), 다른 확장에 저장을 맡길 때는 Entry Save Manager를 비활성화합니다.
3. 열려 있는 엔트리 작품 탭을 모두 새로고침합니다. 기존 페이지에 연결된 함수와 예약된 복원 작업이 남지 않도록, 설정 변경 후 새 페이지 컨텍스트에서 선택한 확장만 시작합니다. 저장하지 않은 진행도는 새로고침하면 사라질 수 있으므로 전환은 진행을 마무리한 뒤 합니다.
4. 검증용 작품에서 저장 후 다시 실행하여 값이 복원되는지 확인합니다. 같은 프로필·origin·namespace를 사용하면 기존 저장본을 이어 읽습니다.

예를 들어 Entry Save Manager와 편집 보조 확장에 모두 저장 기능이 있다면, Entry Save Manager에 저장을 맡기고 편집 보조 확장의 저장 기능만 끕니다. 편집 보조 확장에 저장을 맡기려면 Entry Save Manager를 비활성화한 뒤 페이지를 새로고침합니다.

이 과정에서 저장 데이터를 초기화하거나 `@` 변수 이름을 바꿀 필요는 없습니다. 데이터 삭제는 중복 실행을 해결하지 못하고 진행도만 지웁니다.

### 7.3. 호환 확장 개발자가 제공할 동작

설정에 저장 기능 활성화 여부를 두고, 끌 때는 **저장·불러오기 전체를 다른 확장에 맡기는 모드**로 처리하세요. 아래는 새 확장에서 구현할 동작이며, 현재 Entry Save Manager에 이 설정이 있다는 뜻은 아닙니다.

| 기능 | 직접 처리할 때 | 다른 확장에 맡길 때 |
| --- | --- | --- |
| `@저장` / `@가져오기` | 자기 저장·복원 로직 실행 | 자기 저장·복원 로직 실행 안 함 |
| 실행 시작 자동 복원 | 실행당 한 번 처리 | 복원 타이머 예약·실행 안 함 |
| `@확장프로그램` 변수 | 실행 시 `1` 설정 | 값을 변경하지 않음. 기능을 껐다고 `0`으로 덮어쓰지 않음 |
| 엔진·함수 재연결 감시 | 자기 연결을 관리 | 저장 기능의 감시·재후킹 중단 |
| 데이터 조회 | 가능 | 저장본 목록·내용을 읽기만 하는 조회는 가능 |
| 저장본 편집·삭제·백업 복원 | 별도 관리 작업으로 처리 | 실행 중 자동으로 수행하지 않음. 사용자 요청 시 작품 실행을 멈춘 상태에서 처리 |

함수를 감싸는 다른 기능이 남아 있다면 기존 함수를 원래 `this`·인자로 정확히 한 번 호출하고 반환값을 유지합니다. 저장 기능을 껐다고 작품의 원래 함수 실행까지 막으면 안 됩니다.

실행 중 설정 변경을 지원한다면 정리는 다음 순서로 구현합니다.

1. 자기 저장 기능을 먼저 비활성 상태로 표시합니다. 이후 실행되는 콜백은 이 상태를 확인하고 저장·복원을 건너뜁니다.
2. 대기 중인 자동 복원 타이머, 폴링, 재시도, 저장 기능의 이벤트 리스너를 정리합니다. 이미 시작된 비동기 작업도 완료 직전에 현재 활성 상태와 작업 세대를 확인해야 합니다.
3. 자기 래퍼가 현재 함수일 때만 원본을 복구합니다. 다른 확장이 그 위를 감쌌다면 상대 래퍼를 덮어쓰지 말고, 남아 있는 자기 래퍼가 원본 호출만 전달하도록 비활성화합니다. v1.3.10 개발안의 `releaseFunctionHook`이 이 방식을 사용합니다.
4. 저장 담당자를 바꾸는 경우에는 페이지 새로고침 후 활성화하는 것을 기본으로 합니다. 실행 도중 새 담당자가 자동 복원을 다시 수행하면 현재 진행 값을 덮어쓸 수 있습니다.

호환 확장은 자체 식별자를 사용합니다. `window.__entrySaveManagerLoaded`, 전역 `ESM`, `_isSaveMgrHook`을 복사하거나 조작해서 상대 확장의 실행을 막지 마세요. 시작할 때 상대 플래그를 한 번 확인하는 것만으로는 나중에 주입된 확장까지 조정할 수 없습니다.

### 7.4. 자동으로 담당자를 정하려면

사용자가 기능을 끄지 않아도 공존하게 하려면 **모든 참여 확장이 따르는 공통 실행 조정기**가 추가로 필요합니다. 다음은 이를 새로 구현할 때의 설계 조건이며, 공개 코드나 v1.3.10 개발안에 구현된 API·잠금 규약은 아닙니다.

1. **공통 등록 위치:** 실제 `Entry`가 있는 프레임의 MAIN world에서 하나의 조정기를 공유합니다. 각 확장은 고유한 구현 ID와 지원하는 조정 규약 버전을 등록합니다. 확장별 Isolated world에 각각 둔 플래그로는 공통 담당자를 정할 수 없습니다.
2. **담당자 하나:** 같은 문서·런타임 프레임·작품 ID·namespace에 대해 활성 담당자는 하나입니다. 명시적인 사용자 선택을 우선하고, 선택이 없으면 준비된 구현 중 먼저 소유권을 얻은 하나를 유지하는 등 동일한 선정 규칙을 사용합니다. 뒤늦게 시작한 확장이 기존 담당자를 빼앗지 않도록 합니다.
3. **동시 획득 방지:** 담당자 확인과 등록 사이에 비동기 대기를 넣지 않는 등 획득 연산을 하나로 처리합니다. 각 구현이 “담당자가 없음”을 따로 확인한 뒤 모두 활성화하는 구조는 피합니다. 영구 `localStorage`에 단순 불리언 잠금을 남기는 방법도 사용하지 않습니다. 탭 종료 후 남는 값이나 다른 탭과의 경합을 해결하지 못합니다.
4. **부작용 직전 확인:** 담당자만 함수 후킹·저장·가져오기·자동 복원·상태 변수 설정을 수행합니다. 타이머나 비동기 작업은 실행 직전 소유권 토큰과 컨텍스트 세대가 아직 유효한지 확인합니다. 대기 중인 확장은 후킹하거나 서로 재후킹하지 않습니다.
5. **명시적인 해제:** SPA 작품 이동, 기능 끄기, 재초기화 시 옛 컨텍스트를 비활성화하고 자기 작업을 정리한 뒤 자기 소유권만 해제합니다. 엔진 교체도 담당 구현이 처리하며, 다른 구현이 동시에 복원을 시작할 이유로 삼지 않습니다.
6. **담당자 전환:** 기본은 다음 새로고침에서 다시 선정하는 것입니다. 실행 중 인계를 지원하려면 기존 작업 정리와 활성 소유권이 하나뿐임을 먼저 보장하고, 해당 실행에서 이미 복원했는지도 전달해야 합니다. 단순히 응답이 늦다는 이유로 두 번째 담당자를 활성화하지 않습니다.

기존 Entry Save Manager처럼 이 조정기에 참여하지 않는 구현과는 위 절차만으로 자동 공존을 보장할 수 없습니다. 감지 가능한 흔적이 있더라도 정상 동작 여부를 확정할 수 없고, 흔적이 없다고 다른 저장 확장이 없다고 단정할 수도 없습니다. 그런 조합에는 7.2절의 수동 선택 절차를 적용하고, 자동 조정을 지원한다고 표시하지 않습니다.

조정기의 범위가 같은 프레임 안이라면 **같은 작품을 여러 탭에서 실행하는 충돌은 별개**입니다. 서로 다른 탭에서도 같은 저장 키를 쓸 수 있고 현재 저장 형식은 마지막 쓰기만 유지합니다. 프레임 내 담당자 선정만으로 탭 간 충돌까지 해결했다고 보지 마세요.

### 7.5. 공용 저장본 관리

현재 작품 초기화는 해당 namespace의 키만 `removeItem()`합니다. Entry Save Manager 팝업의 전체 초기화는 접근 가능한 프레임의 `entry_save_`로 시작하는 키를 모두 삭제하므로, 다른 호환 확장이 쓴 저장본도 함께 지워집니다. 확장 전용 설정·백업은 이 접두사 밖에 보관하세요. 사이트의 다른 데이터를 지우는 `localStorage.clear()`는 사용하지 않습니다.

## 8. 호환성 확인 절차

검증용 작품과 별도 브라우저 프로필에서 진행합니다. A는 Entry Save Manager, B는 새 확장입니다. 한 번에 저장 기능을 담당하는 확장 하나만 켜고 전환 후 페이지를 새로고침하세요. 아래 항목은 구현자가 수행할 확인 절차이며, 모든 제3자 확장에서 검증을 마쳤다는 뜻은 아닙니다.

| 확인 | 기대 결과 |
| --- | --- |
| A로 저장 → B로 실행, B로 저장 → A로 실행 | 양방향으로 같은 변수·리스트 값 복원 |
| 숫자·문자열·불리언·`null`, 빈 리스트 | 타입·순서·빈 상태 보존 |
| 일반 변수/리스트, `@확장프로그램` 변수 | 저장본에서 제외. 기존 저장본에 플래그가 있어도 덮어쓰지 않음 |
| 같은 ID로 `/ws/`와 `/project/`에서 다른 값 저장 | 두 저장본 분리. `/noframe/`은 작품보기 저장본 사용 |
| `/ws/`의 자식 `/iframe/`에서 저장 | 부모가 만들기라는 정보를 반영하여 `entry_save_ws_<id>` 사용 |
| 다른 작품에서 같은 이름/다른 ID로 가져오기 | 이름으로 복원. 같은 ID/다른 이름의 대상은 유지 |
| `/ws/`에서 다른 ID 가져오기 / 현재 ID 가져오기 | 각각 다른 작품의 project 키 / 자기 ws 키 사용 |
| 현재 대상 이름에서 `@` 제거 또는 예약 변수로 변경 | 예전 ID가 일치해도 복원 제외 |
| 잘못된 JSON, 객체 값, 중첩 배열, 없는 대상 | 잘못된 JSON은 중단, 잘못된 항목은 스킵, 유효한 항목은 복원 |
| 정지→실행, 일시정지→재개, 전체화면, SPA 작품 이동 | 필요한 실행에서 한 번 복원. 이전 작품 후킹·타이머 정리 |
| `@가져오기` 인자로 변수/계산식 사용, 함수 편집·재생성 | 평가된 최신 인자와 최신 함수 정의 사용 |
| 현재 작품 초기화 / 전체 초기화 | 각각 현재 namespace만 / `entry_save_` 접두사 저장본 삭제 |

여러 확장의 공존을 지원하는 구현은 다음 항목도 확인합니다. 자동 조정 항목은 7.4절의 조정기를 실제로 구현한 조합에만 적용합니다.

| 확인 | 기대 결과 |
| --- | --- |
| A는 저장 담당, B는 저장 기능 끔 | A만 저장·가져오기·자동 복원 수행. B의 다른 도구 기능은 계속 동작 |
| A를 끄고 B로 전환한 뒤 새로고침 | 기존 저장본을 이어 읽음. 데이터 초기화 불필요 |
| 자동 복원 대기 중 저장 기능 끄기 | 옛 콜백이 나중에 값을 덮어쓰지 않음. 꺼진 구현은 상태 변수를 `0`으로 바꾸지 않음 |
| 다른 확장이 감싼 함수에서 자기 저장 기능 해제 | 상대 래퍼와 작품의 원래 함수 실행·반환값 보존 |
| 자동 조정: A/B 주입 순서 반전·초기화 시점 겹침 | 각 경우 담당자는 하나이며, 대기 구현의 저장·복원 횟수는 0 |
| 자동 조정: SPA 이동·엔진 교체·담당자 전환 | 옛 컨텍스트 작업 중단, 새 컨텍스트의 단일 담당 유지, 같은 실행의 복원 중복 방지 |
| 조정 미지원 확장이 함께 활성화됨 | 자동 공존을 보장한다고 안내하지 않고, 사용자가 저장 기능 하나를 선택하도록 안내 |

이 저장소의 기존 검증은 저장소 루트에서 `npm run verify`로 실행합니다. [shared.test.js](../ES/tests/shared.test.js)는 키 규칙을, [inject.test.js](../ES/tests/inject.test.js)는 저장·복원·후킹 동작을 확인합니다. Node의 VM 테스트 통과와 실제 엔트리 사이트에서의 확인은 별개이며, 실사이트 확인 방법은 [테스트 가이드](공통/entry-extension-real-site-testing.md)를 참고하세요.
