이 문서는 v1.2.x → v1.3.9 동안 발생한 모든 버그·요구사항·설계 결정과 그 해결책을 시간 순으로 기록합니다.

## v1.3.0 — `/ws/` ↔ `/project/` namespace 분리 {#v130}

### 문제

엔트리는 같은 작품 ID를 가진 두 종류의 URL을 가집니다:
- `https://playentry.org/ws/<id>` — 워크스페이스(만들기·편집·테스트)
- `https://playentry.org/project/<id>` — 작품보기(플레이어 환경)

기존 v1.2.x는 `entry_save_<projectId>` 형태의 키 하나만 사용 → 두 페이지가 **동일 저장본을 공유**. 결과적으로:
- 제작자가 워크스페이스에서 테스트한 변수값이 그대로 플레이어 환경에 노출
- 반대로 플레이어가 만든 진행도가 제작 환경을 오염

### 요구사항

- 두 페이지의 저장본을 독립된 namespace로 분리
- 기존 v1.2.x 사용자 데이터는 만들기(`/ws/`) namespace에 종속(=마이그레이션 불필요)
- `@가져오기` 교차 작품 로드는 **항상 `/project/` namespace에서** (시리즈 작품 플레이어 시나리오)
- 팝업의 "현재 작품 초기화"는 **현재 탭이 속한 namespace만** 삭제

### 해결

1. `shared.js`에 `getPageTypeFromPathname(pathname)` + `buildStorageKey(pageType, projectId)` 헬퍼 추가
2. 처음 매핑(v1.3.0):
   - `/ws/<id>` → `entry_save_<id>` (레거시 키 유지)
   - `/project/<id>` → `entry_save_project_<id>` (신설)
3. 자식 `/iframe/<id>`은 부모로부터 postMessage 핸드셰이크로 pageType 받음 → [Entry pageType 핸드셰이크 설계](공통/entry-page-type-handshake.md)
4. inject.js의 `loadData(sourceProjectId)`: 인자 없으면 자기 namespace, 인자 있으면 강제로 project namespace
5. popup.js: `currentPageType`을 캐시해 reset 버튼이 현재 namespace 키만 삭제

**놓쳤던 함정**: 처음에는 `var pageType = ...` 같은 module-level 변수로 흩뿌렸다가, 핸드셰이크 timing이 복잡해지자 → v1.3.3에서 `ptState` 객체로 묶음.

## v1.3.0 직후 — fallback이 shared.js를 안 가져오던 잠복 버그

### 증상

페이지 로드 후 `Uncaught ReferenceError: ESM is not defined` 에러. 모든 후킹 동작 안 함. v1.2.x에서는 동작하던 환경에서 갑자기 깨짐.

### 진단

콘솔 로그 분석:
```
content.js:130 [Entry Save Manager] inject.js 폴백 삽입 완료
inject.js:27 Uncaught ReferenceError: ESM is not defined
```

→ playentry.org 환경에서 manifest의 `world: "MAIN"` content_scripts가 **firing 안 함** (alway 그랬음). content.js의 `injectScriptFallback()`이 폴백 경로로 inject.js만 주입했는데, 의존성인 shared.js를 같이 주입하지 않아 `var ESM`이 정의되지 않음.

v1.2.x에서는 잠복하던 버그(MAIN world가 firing하던 환경에선 안 보였음). 환경/Chrome 변경으로 노출.

### 해결

`content.js`의 `injectScriptFallback()`을 수정 — shared.js를 먼저 주입하고 그 onload 콜백에서 inject.js 주입:

```js
function injectScriptFallback() {
  injectOneScript('shared.js', function () {
    injectOneScript('inject.js', function () { /* done */ });
  });
}
```

manifest의 `web_accessible_resources`에 이미 두 파일 모두 포함되어 있어 추가 변경 불필요.

## /project/ 자동 실행이 안 일어남 (사용자 제스처 대기)

### 증상

inject.js가 정상 후킹됐고 watchEngineState도 시작됐는데 `@확장프로그램`이 1로 안 변경됨. 자동 로드도 안 일어남.

### 진단

```
[ESM] Entry.engine.state: stop
[ESM-DBG][inject] watchEngineState 시작 — 초기 상태: stop
```

→ 엔진이 영원히 'stop' 상태에 머무름. `loadData`/`setExtensionStatusFlag`는 stop→run 전이 시 트리거되므로 호출 안 됨.

콘솔의 다른 경고가 단서:
```
The AudioContext was not allowed to start. It must be resumed (or created) after a user gesture on the page.
```

→ Chrome의 autoplay 정책으로 user gesture 없이는 사운드 초기화가 막히고, Entry는 그 단계에서 더 진행을 못 함. 일부 작품은 사용자 클릭까지 게임 시작을 미룹니다.

### 해결 (코드 변경 없음)

- 이는 우리 확장의 버그가 아님 — 작품/Chrome 동작
- 사용자가 페이지 어딘가 클릭하거나 Play 버튼을 누르면 정상 동작
- 콘솔에서 `Entry.engine.toggleRun()` 직접 호출도 가능

이 통찰은 [05-디버깅-가이드.md](05-디버깅-가이드.md) "흔한 증상" 섹션에 영구 기록.

## v1.3.2 — `/noframe/<id>` 페이지 지원 {#v132}

### 요구

> "주소가 https://playentry.org/noframe/69b3ef8e0075070c7c1d0aca 일때 https://playentry.org/project/69b3ef8e0075070c7c1d0aca 와 똑같이 동작하도록 만들어줘."

`/noframe/`은 자식 iframe 없이 top frame에 직접 runtime이 호스팅되는 작품보기 변형 (외부 임베딩용 추정).

### 영향 분석

기존 코드는 `/project/`, `/iframe/`, `/ws/`만 인식 → `/noframe/`에서:
- `extractProjectId`가 `null` 반환 → 키 생성 실패
- `getPageTypeFromPathname`이 `null` → ws 폴백으로 잘못된 키 사용
- `isProjectPage`가 false → `waitForEntry`가 engine/block 대기 안 함 → 후킹 타이밍 어긋남
- content.js의 SPA URL 변경 감지가 noframe 진입 무시

### 해결 (4지점)

1. **`shared.js:18`** `extractProjectId` regex에 `noframe` 추가
2. **`shared.js:32`** `getPageTypeFromPathname`에 `'/noframe/' → 'project'` 매핑
3. **`inject.js:60`** `isProjectPage`에 `/noframe/` 포함
4. **`content.js:200`** SPA URL 감지에 `/noframe/` 추가

manifest는 이미 `playentry.org/*` 광범위 매처라 변경 불필요.

`/noframe/`은 top frame이라 핸드셰이크 불필요 — pathname에서 즉시 'project' 결정.

## v1.3.4 — v1.3.0 → v1.3.1 데이터 자동 마이그레이션 {#v134}

### 증상

사용자 보고: "변수가 적용이 안되는 문제가 있어." 콘솔 진단:
```js
Object.keys(localStorage).filter(k => k.startsWith('entry_save_'))
// ['entry_save_ws_<id>', 'entry_save_project_<id>', 'entry_save_<id>', ...]
```

`entry_save_<id>`(v1.3.1+ project 키)와 `entry_save_project_<id>`(v1.3.0 project 키)가 둘 다 존재.

### 진단

v1.3.1 키 명명 반전의 후폭풍 — 사용자가 v1.3.0에서 저장한 데이터가 `entry_save_project_<id>`에 있는데, v1.3.1+ `/project/`는 `entry_save_<id>`에서 읽어 그 데이터가 고아 상태.

### 해결

`inject.js`에 `readWithV130Migration(targetProjectId, isCrossProject)` 헬퍼 추가:
- 새 키에 데이터가 있으면 그대로 사용
- 없으면 `entry_save_project_<id>` 확인 → 있으면 새 키로 copy + 옛 키 삭제 (자기 페이지 로드인 경우)
- `@가져오기` 교차 로드일 때는 마이그레이션 안 하고 읽기만 (다른 작품의 데이터를 마음대로 옮기지 않음)

```js
function readWithV130Migration(targetProjectId, isCrossProject) {
  const key = isCrossProject
    ? ESM.buildStorageKey('project', targetProjectId)
    : getStorageKey();
  let raw = localStorage.getItem(key);
  if (raw) return { key, raw };

  const v130Key = ESM.STORAGE_KEY_PREFIX + 'project_' + targetProjectId;
  const v130Raw = localStorage.getItem(v130Key);
  if (!v130Raw) return { key, raw: null };

  if (!isCrossProject) {
    localStorage.setItem(key, v130Raw);
    localStorage.removeItem(v130Key);
  }
  return { key: isCrossProject ? v130Key : key, raw: v130Raw };
}
```

### 한계

이 마이그레이션은 사용자가 한 번이라도 게임을 실행해 자동 로드가 트리거될 때 동작. 자동 로드가 발생 안 하면 마이그레이션도 안 됨 — 보통 사용자가 작품 페이지에 진입해서 게임을 시작하면 자연스럽게 처리.

### 현재 상태

v1.3.6에서 v1.3.2 동등 상태로 롤백되며 `readWithV130Migration` 헬퍼도 제거됨. v1.3.9 기준 현재 코드는 `entry_save_project_<id>`를 자동 이관하지 않는다. 이 절은 v1.3.4의 역사 기록으로만 본다.

## v1.3.5 — 중대 버그: MAIN world에서 ESM 미정의 {#v135}

### 증상

v1.3.4 마이그레이션 추가 후에도 변수 적용이 안 됨. 사용자 콘솔 진단 결과 (요약):
```
top __esmL: true | top ESM: object
iframe __esmL: true | iframe ESM: object | iframe Entry: true
@확장프로그램: { name: '@확장프로그램', value: 0 }
toggleRun 후킹됨: false
func_9hs9._isSaveMgrHook: false
```

inject.js IIFE는 실행됐는데(`__esmL: true`) **toggleRun과 @저장 함수 후킹이 둘 다 설치되지 않음** → 자동 로드도 트리거 안 됨.

확장 재로딩 후 콘솔 캡처에서 진짜 원인 발견:
```
VM9350 inject.js:75 Uncaught ReferenceError: ESM is not defined
```

inject.js:75는 `const ptState = { type: ESM.getPageTypeFromPathname(...) }` 라인. ESM이 없어서 IIFE가 line 75에서 throw → 후킹 코드까지 못 감.

### 진짜 원인

**MV3 `world: "MAIN"` content_scripts는 각 파일을 별도 wrapper에서 실행**합니다. 즉 manifest에 `js: ["shared.js", "inject.js"]`로 적어도, 두 파일이 별도 wrapper에서 따로 실행돼서 shared.js의 `var ESM = {...}`이 글로벌이 아니라 wrapper 내부 지역 변수가 됩니다. inject.js (같은 MAIN world의 별도 파일)에서는 ESM을 못 봅니다.

이전 세션에서는 manifest MAIN world가 firing 안 하고 fallback의 `<script>` 태그만 동작 → fallback 스크립트는 wrapper 없이 page global로 들어가 OK였음. 환경 변화로 manifest MAIN world가 부분적으로 firing하면서 충돌 노출.

### 해결

`shared.js`의 ESM 선언을 `var ESM = {...}` → `window.ESM = {...}`로 변경. 명시적으로 window에 attach하여 wrapper 유무와 무관하게 모든 환경(MAIN world / Isolated world / fallback / popup)에서 일관 접근.

```js
// before — MAIN world wrapper 안에 갇힘
var ESM = { STORAGE_KEY_PREFIX: 'entry_save_', ... };

// after — 명시적 글로벌
window.ESM = { STORAGE_KEY_PREFIX: 'entry_save_', ... };
```

### 교훈

- **MV3 content_script의 `world: "MAIN"`은 각 파일을 격리합니다**. 파일 간 변수 공유는 반드시 `window.X = ...` 또는 `globalThis.X = ...`로 명시.
- 자세한 함정 정리는 [MV3 content_scripts 함정 정리](공통/mv3-content-script-pitfalls.md)
- 회귀 진단의 결정타는 **확장 재로딩 후 첫 콘솔 출력**이었음 — 그 전엔 캐시된 옛 inject.js가 IIFE 플래그를 점령해 새 IIFE가 silent skip → 진짜 원인 보이지 않았음. [05-디버깅-가이드.md](05-디버깅-가이드.md) "확실한 재로딩 절차"

## v1.3.6 — v1.3.3~1.3.5 회귀 → v1.3.2로 롤백 {#v136}

### 증상

v1.3.5 적용 후에도 사용자 보고 "여전히 잘 동작 안 함". 진단 결과:
- inject.js IIFE 실행됨 (`__esmL: true`)
- 하지만 `toggleRun`과 `@저장` 함수 후킹이 둘 다 미설치
- `@확장프로그램` 1로 안 변경, 자동 로드 안 됨

### 진단의 함정

v1.3.5에서 세웠던 가설(`var ESM` → MAIN world wrapper에 격리)은 **틀렸을 가능성 높음**. 작동하던 v1.3.2가 `var ESM`을 그대로 쓰면서 정상 동작했기 때문. 진짜 원인은 v1.3.3~1.3.5에서 추가한 다음 중 하나로 추정:

1. **Phase A/B/C 리팩토링** — `tryHookSave`/`tryHookLoad` 통합(`tryHookFunctionBlock`), 모듈 상태 그룹화 (`ptState`, `saveHook`/`loadHook`)에서 미묘한 회귀
2. **`readWithV130Migration` 추가** — loadData의 진입 지점 변경
3. **`console.log` → `debug()` 전환** — 일부 중요 메시지가 운영 모드에서 사라져 진단 자체가 어려워짐
4. **`var ESM` → `window.ESM` 변경** — 검증 안 된 가설로 인한 변경

### 결정: 안전 우선 롤백

사용자 요청: "잘 동작 했던 버전(`Entry Save/Entry Save/ES/`)을 참고해서 고쳐줘"

→ inject.js, content.js, shared.js를 **v1.3.2 동등한 상태로 복원**. manifest.json만 버전 1.3.6으로 업데이트.

popup.* 파일은 working 버전과 차이 없어 변경 불필요.

### 교훈

1. **검증 안 된 가설로 코드를 고치지 말 것** — 사용자 환경에서 실제로 재현 가능한 진단 후에만 수정
2. **단일 회기 내에 너무 많은 변경 금지** — A/B/C/콘솔/마이그레이션/window.ESM이 한꺼번에 들어가면 회귀 원인 분리 어려움
3. **마지막 안정 버전 보관** — 이번처럼 별도 폴더(`Entry Save/Entry Save/ES/`)에 working snapshot이 있어서 복원 가능. 향후에도 매 안정 릴리즈마다 snapshot 별도 보관 권장
4. **리팩토링은 행동을 보존해야 함** — Phase A/B/C가 syntax check를 통과해도 런타임 동작이 깨질 수 있음 — 실제 페이지에서 자동 로드 / 후킹이 모두 동작하는지 확인해야 검증 완료

### 향후 변경 시 절차 (다음에 같은 실수 안 하려고)

1. 변경 **한 가지**를 적용
2. 확장 reload + 페이지 새로고침
3. 시나리오 1~7 ([05-디버깅-가이드.md](05-디버깅-가이드.md) "배포 전 셀프 테스트") 모두 통과 확인
4. 통과 시 → 다음 변경
5. 통과 안 되면 → 즉시 revert

여러 변경을 한꺼번에 적용하지 말 것. 한꺼번에 들어간 변경은 회귀 원인 격리가 거의 불가능.

## v1.3.7 — 작품보기 전체화면(⛶) 시 `Entry.engine` 교체로 후킹 끊김 {#v137}

### 증상

사용자 보고: "엔트리 업데이트로 작품 실행 페이지에서 전체화면을 누르면 새로고침되면서 확대되는 형태로 변했는데, 이로 인해 확장이 정상 동작하지 않는다." 재현 작품: `@확장프로그램`이 0이 아니게 될 때까지 대기 → `@리스트`에 현재 시간 저장 → `@저장` 호출.

### 진단 (실사이트 브라우저 계측)

`/project/<id>` 최상위 콘솔에서 자식 iframe(`window.frames[0]`, **동일 출처 playentry.org**)의 `Entry`·`engine`·변수·후킹을 직접 스냅샷하며 전체화면을 눌러 관찰. 객체에 랜덤 태그를 붙여 정체성 변화를 추적.

전체화면 전후 비교:

| 항목 | 전체화면 전 | 전체화면 후 |
|---|---|---|
| iframe 세션 `?s=` | 동일 | **동일** (iframe 리로드 아님) |
| `Entry` 객체 | 동일 | **동일** (inject.js 재실행 안 됨) |
| **`Entry.engine` 객체** | 예: `gnqlx` | **`gqksx` (새 객체로 교체!)** |
| 엔진 상태 / 변수 | run / 값 있음 | **stop / 0으로 리셋** (▶ 버튼 재등장) |
| `@저장` 블록 후킹(`_isSaveMgrHook`) | true | **true (생존)** |
| `Entry.engine.toggleRun` 후킹 | 우리 래퍼 | **native (무효화)** |

### 진짜 원인

엔트리 작품보기 전체화면 버튼(⛶, playentry 사이트 chrome)은 런타임 iframe에 `iframe.requestFullscreen()`을 걸고, **그 과정에서 `Entry.engine`을 새 객체로 통째 교체하고 프로젝트를 재초기화**(변수 리셋, stop)한다. iframe도 inject.js IIFE도 리로드되지 않으므로:

- `Entry.block`에 건 `@저장`/`@가져오기` 블록 후킹은 **전역이라 생존** → 저장 자체는 됨
- 하지만 `watchEngineState`가 **옛 engine 객체**에 건 `toggleRun` 후킹은 새 engine에선 무효 → 즉각 감지(load/`@확장프로그램` 설정)가 끊김
- 복구가 500ms 폴링(`Entry.engine.state`를 전역으로 재조회)이 `stop→run` 에지를 잡느냐에만 의존하는 **취약 상태**. 새 engine이 에지 없이 바로 run이면 `@확장프로그램`이 0에 멈춰 작품의 대기 루프가 영영 안 풀림

> upstream `entryjs-develop/src/class/engine.js`의 `toggleFullScreen`은 popup+CSS 클래스(리로드 없음)라 라이브 동작과 다름 → 작품보기 전체화면은 **playentry 사이트(비공개 React) 핸들러**가 담당. 로컬 엔진 소스만으로는 확정 불가, 실사이트 계측이 필수였다.

### 해결 ([inject.js](../ES/inject.js))

`hookEngineToggleRun(engine)` 헬퍼를 추출(시그니처 `_isSaveMgrEngineHook`로 중복 래핑 방지)하고, **폴링 루프에 engine 객체 교체 감지**를 추가:

```js
if (eng !== hookedEngine) {            // Entry.engine이 새 객체로 교체됨
  hookEngineToggleRun(eng);            // 새 engine에 toggleRun 재후킹
  if (eng.state === 'run') {           // 에지 없이 이미 run이면(에지 누락 케이스)
    loadData(); setExtensionStatusFlag(); // 즉시 복원
  }
  prevState = eng.state;
}
```

`@저장`/`@가져오기` 블록 후킹은 생존이 확인되어 손대지 않음 (검증된 범위만 수정 — v1.3.6 교훈 준수).

### 검증 (Claude in Chrome 실사이트)

1. **수정 로직 라이브 증명**: 주입 워처로 실제 전체화면 교체(`gfz6j`→`gvsi5`)를 재현 → 교체 감지·재후킹·새 engine 래퍼 발화까지 확인
2. **빌드 확장 reload 후 end-to-end**: 교체 직후 새 engine `engHook=false` → ~300ms 만에 `true`(자동 재후킹), 재실행 시 `@확장프로그램=1`·`@리스트` 복원·작품 정상 진행 확인

### 교훈

- **`Entry.engine`은 교체될 수 있다** (전체화면 등). engine 객체에 건 후킹은 정체성 변화를 감지해 재설치해야 한다. 가능하면 전역(`Entry.block`)에 걸어 생존시키거나, 폴링에서 `eng !== hooked` 가드로 재후킹.
- 작품보기 런타임 iframe은 `/project/`와 **동일 출처**라 최상위 콘솔에서 `frames[0].Entry`로 직접 계측 가능 — 객체 태깅으로 정체성 추적이 진단의 결정타.
- 로컬 `entryjs-develop`은 **엔진**이지 작품보기 사이트 chrome이 아니다. 사이트발 동작(전체화면 등)은 실사이트 계측으로만 확정.

## 시간순 패턴 — 환경 변화에 노출되는 잠복 버그

이 프로젝트의 핵심 패턴: **manifest MAIN world content_script의 동작이 playentry.org 환경에서 일관되지 않음**. 시기마다 다음 중 하나로 동작:

1. MAIN world manifest 정상 firing → manifest의 `[shared.js, inject.js]` 순서대로 실행
2. MAIN world manifest 안 firing → fallback이 `<script>` 태그로 두 파일 주입
3. MAIN world manifest 부분 firing → inject.js만 실행되거나, 별도 wrapper에 격리

각 시나리오마다 다른 버그가 노출:
- (1)이 항상 동작한다고 가정한 v1.2.x → (2) 환경에서 fallback이 shared.js를 안 주입하던 버그 노출
- (1) → (3) 변화에서 `var ESM` wrapper 격리 버그(v1.3.5) 노출

**원칙**: shared.js는 어떤 컨텍스트에서도 동작해야 함. 특히 변수 공유는 명시적 `window.X` 사용. fallback은 모든 의존성을 직접 주입.
