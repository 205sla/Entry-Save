# 스토리지 키 규칙 변천사 + 마이그레이션 정책

localStorage key 명명 규칙은 v1.2.x → v1.3.9 동안 두 번 바뀌었습니다. 이 문서는 각 시점의 규칙·이유·호환성·마이그레이션 경로를 정리합니다.

---

## 현재(v1.3.9) 규칙

```js
// shared.js:54
buildStorageKey: function (pageType, projectId) {
  if (pageType === 'ws') {
    return this.STORAGE_KEY_PREFIX + this.NAMESPACE_WS + projectId;  // 'entry_save_ws_<id>'
  }
  return this.STORAGE_KEY_PREFIX + projectId;  // 'entry_save_<id>'
}
```

| 페이지 (top frame) | pageType | 사용 키 |
|---|---|---|
| `/project/<id>` | `'project'` | **`entry_save_<id>`** (기본, prefix 없음) |
| `/noframe/<id>` | `'project'` | **`entry_save_<id>`** (project와 같은 namespace) |
| `/ws/<id>` | `'ws'` | `entry_save_ws_<id>` |
| `/iframe/<id>` (부모 결정) | 부모 따라감 | 부모 따라감 |
| `@가져오기(<otherId>)` | (강제 'project') | `entry_save_<otherId>` |

핵심:
- **prefix 없음 = 기본 = project** (대다수 사용자/플레이어 시나리오)
- **`ws_` prefix만 워크스페이스 전용**
- `@가져오기`는 호출 페이지 무관 항상 project — 시리즈 작품이 모두 `/project/`에서 플레이되는 시나리오

## 변천 history

### v1.2.x — namespace 분리 없음

```
모든 페이지 → entry_save_<id>
```

`/ws/`와 `/project/`가 같은 키를 공유 → 제작자 테스트 데이터와 플레이어 진행도가 섞이는 문제. v1.3.0에서 분리 결정.

### v1.3.0 — 첫 분리 (ws가 기본 키 유지)

```
/ws/      → entry_save_<id>            (레거시, 기존 데이터 보존)
/project/ → entry_save_project_<id>    (신설)
```

이유: 기존 v1.2.x 사용자 데이터를 어디에 둘지 결정 필요. 사용자 요청: "기존 저장본은 만들기 페이지에 종속". → ws가 레거시 키 형식 유지.

### v1.3.1 — 반전 (project가 기본 키)

```
/ws/      → entry_save_ws_<id>   (신설 prefix)
/project/ → entry_save_<id>      (기본, prefix 없음)
```

이유 (사용자 요청): 대다수 사용자가 `/project/`에 있고, 거기가 기본이어야 자연스러움. v1.2.x 데이터(`entry_save_<id>`)는 자동으로 project namespace로 인계 — 의도와 일치.

부수 효과: v1.3.0에서 `/project/`로 저장한 데이터(`entry_save_project_<id>`)는 **고아** 상태. v1.3.4에서 마이그레이션 추가.

### v1.3.2 — `/noframe/` 추가

키 규칙 자체는 변경 없음. `/noframe/`이 `/project/`와 같은 namespace 사용하도록 매핑만 추가.

## 마이그레이션 정책 {#마이그레이션}

### v1.2.x → v1.3.0 (자동, 무 코드)

- v1.2.x 키: `entry_save_<id>`
- v1.3.0의 /ws/ 키: `entry_save_<id>` (같음)
- 결과: /ws/에서 자동 로드 시 그대로 사용. /project/에서는 안 보임 (다른 키)
- 코드 액션 불필요

### v1.2.x → v1.3.1+ (자동, 무 코드)

- v1.2.x 키: `entry_save_<id>`
- v1.3.1+의 /project/ 키: `entry_save_<id>` (같음)
- 결과: /project/에서 자동 로드 시 그대로 사용. /ws/에서는 안 보임
- 코드 액션 불필요 (사용자 입장에서 조용한 인계)

### v1.3.0 → v1.3.1+ (현재 자동 마이그레이션 없음)

- v1.3.0 /project/ 키: `entry_save_project_<id>`
- v1.3.1+ /project/ 키: `entry_save_<id>`
- v1.3.0 /ws/ 키: `entry_save_<id>`
- v1.3.1+ /ws/ 키: `entry_save_ws_<id>`

**충돌 가능성**:
- `entry_save_<id>`는 v1.3.0에선 ws 데이터, v1.3.1+에선 project 데이터로 의미가 바뀜
- v1.3.0에서 /ws/와 /project/ 둘 다 사용한 사용자는 두 키가 모두 존재할 수 있음
- 자동 마이그레이션은 위험 — 잘못 옮기면 데이터 섞임

**현재 정책 (v1.3.9)**: 자동 마이그레이션 없음
- /project/ 자동 로드: `entry_save_<id>`만 읽음
- /ws/ 자동 로드: `entry_save_ws_<id>`만 읽음
- `entry_save_project_<id>`(v1.3.0 project 키)는 자동 copy/delete 하지 않음

역사적으로 v1.3.4에서 `readWithV130Migration(targetProjectId, isCrossProject)` 헬퍼가 도입되어 `entry_save_project_<id>`를 lazy copy/delete 하려는 시도가 있었지만, v1.3.6에서 v1.3.2 동등 상태로 롤백되며 현재 코드에는 존재하지 않는다. 대상 코호트가 매우 작고, 사용자가 새 버전에서 다시 저장하면 현재 키(`entry_save_<id>` 또는 `entry_save_ws_<id>`)로 자연스럽게 자가치유된다.

수동 확인/정리가 필요한 경우는 [05-디버깅-가이드.md](05-디버깅-가이드.md)의 localStorage 진단 스니펫으로 실제 키를 확인한 뒤 진행한다.

### `@가져오기` 교차 작품 정책

- 기본: 새 키(`entry_save_<otherId>`)에서 읽기
- v1.3.0 키(`entry_save_project_<otherId>`) 폴백 없음
- 이유: 교차 작품 가져오기는 현재 공개 작품 기준의 project namespace만 읽는 단순 규칙을 유지한다. 다른 작품의 저장 데이터를 확장이 마음대로 이동시키지 않는다.

## popup.js의 키 처리

### "현재 작품 초기화"

```js
const key = ESM.buildStorageKey(currentPageType, currentProjectId);
await removeKeyFromAllFrames(tab.id, key);
```

현재 페이지의 namespace 키만 삭제. 반대 namespace는 보존. v1.3.0 옛 키도 건드리지 않음.

### "모든 데이터 초기화"

`entry_save_*` prefix 매칭 → 모든 형식 키 삭제 (ws, project, v1.3.0 잔재 모두 포함). prefix가 같으므로 명시적 케이스 분기 필요 없음.

## 디자인 원칙

1. **모든 키는 `entry_save_` prefix로 시작** — popup의 일괄 검색·삭제 안전
2. **단일 진입점 `ESM.buildStorageKey(pageType, projectId)`** — 키 결정 로직 산재 방지
3. **변경 시 마이그레이션 검토** — 자동 이관을 넣을지, 수동 안내로 충분한지 대상 코호트와 충돌 위험을 기준으로 결정
4. **소유자 권한 존중** — 자기 페이지 데이터만 마이그레이션, 교차 작품은 읽기만
